# 戦士 Wave1 ドラフト分析（M8-C.1 の修正前分析）

M8-C で戦士の active が 5 → 15 になった結果、**active 枠 4 の進化到達率が 92.5% → 46.5%** へ落ちた。
その原因を production の `SkillDraftManager` で実測して分類し、どこを直したかを記録する。

計測はすべて `tests/warrior-draft-sim.mjs`（production の抽選器をそのまま駆動する共通ハーネス）で行った。
独自抽選器は使っていない。`Math.random` は 1 度も呼んでいない。

---

## 1. 何を測ったか

| 項目 | 値 |
|------|----|
| seed | 1〜200（`HEAVY=1` で 500〜2000） |
| レベルアップ回数 | 40（既存テストの基準）/ 30 / 60 / 90 |
| active 枠 | 4 / 6 / 8（passive 枠は 4 固定） |
| 戦略 | evolution-first / balanced / random-valid / new-skill-priority / one-build-focus ＋ 素朴（M8-B / M8-C 互換） |
| 使う production | `SkillDraftManager`（open / reroll / banish / skip / pity / synergy）・`SeededRandom`・`poolEligibility`・`SkillCatalog`・実 rarity・実進化条件 |

「素朴」戦略 = 進化候補があれば取り、無ければ候補列の先頭を取る。
M8-B / M8-C の到達率テストと同じ物差しなので、**変更前後を同じ条件で比較できる**。

---

## 2. 46.5% の再現と分解

| 経路 | 枠4 / 40 レベルアップ・進化 1 個以上 |
|------|--------------------------------------|
| `_generate()` 直呼び（M8-C の既存テスト。synergy ctx も pity も無い） | **46.5%** |
| production 経路（`open()` ＋ synergy ctx ＋ pity。reroll/banish/skip 込み） | **62.5%** |
| production 経路 ＋ M8-C.1 の導線補助 | **89.5%** |

つまり 46.5% のうち **約 16pt は「テストが production の経路を通っていなかった」ぶん**、
残りが**本当に production 側に足りていなかったぶん**だった。両方を直した。

---

## 3. 進化 0 の周回で何が起きていたか（枠4 / 40 レベルアップ・94 run）

| 指標 | 進化 0 の run | 進化 1 個以上の run |
|------|---------------|---------------------|
| 取得した active 数 | 4.00 | 4.00 |
| うち進化元（base）| 2.09 | 1.33（進化で置換され消えたぶんを含まない） |
| うち進化を持たない active | 1.91 | 2.67 |
| **所持 base の最高 Lv** | **7.03** | — |
| base Lv8 到達数 | 0.51 | — |
| 補助の必要 Lv を満たしたレシピ数 | 4.85 / 8 | 5.19 / 8 |
| **進化条件の形成数** | **0.00** | 1.11 |
| active 枠が埋まったレベル | 4.9 | 5.3 |
| passive 枠が埋まったレベル | 20.1 | 21.0 |
| base の強化提示回数 | 32.9 | 38.6 |
| 補助の提示回数（新規 / 強化）| 12.3 / 33.2 | 12.7 / 32.4 |
| 進化軸と無関係な候補の提示 | 34.7 | 28.2 |
| 条件成立後の未提示 | 0.00 | 0.00 |
| 候補ゼロ | 0.00 | 0.00 |

**決定的な数字は「所持 base の最高 Lv 7.03」**。
補助（passive）はほぼ揃っている（4.85/8 レシピ）のに、**基礎 active が最後の 1 段階だけ届いていない**。

## 4. 原因の分類

| # | 分類 | 該当 | 根拠 |
|---|------|------|------|
| 1 | base 取得不足 | △ | 4 枠のうち 2.09 が base。取得自体はできている |
| 2 | **base Lv8 不足** | **◎ 主因** | 所持 base の最高 Lv が 7.03。あと 1 段階で届かない |
| 3 | support 取得不足 | × | passive は 20 レベル前後で 4 枠とも埋まる |
| 4 | support Lv 不足 | × | 4.85/8 レシピで必要 Lv を満たしている |
| 5 | 条件成立後の提示不足 | × | 未提示 0.00。成立したら必ず最優先枠で出ている |
| 6 | **slot4 特有の新 active 希釈** | **○ 副因** | 無関係な候補の提示が 34.7 回（成功 run は 28.2 回）。15 種へ増えたぶん 1 種あたりの提示が薄まった |
| 7 | rarity 偏り | △ | `great_cleave`（common・重み 100）へ寄る傾向は M8-B から存在。M8-C で悪化はしていない |
| 8 | simulation 戦略要因 | ○ | 既存テストが `_generate()` 直呼びで synergy / pity / reroll を通していなかった（上表の 16pt ぶん） |
| 9 | data 不具合 | × | 進化条件・プール・rarity に不整合なし（`validate-data` 0 エラー） |
| 10 | **production ロジック不具合** | **◎** | 次節 |

## 5. production 側の接続不良（§優先1 の確認結果）

火 / 氷で使われている M6-F の synergy 補助を戦士で 1 つずつ確認した。

| 補助 | 戦士での接続 |
|------|--------------|
| 所持 base → 必要 support の重み | **接続済み**（`evolutionPartnerIds` が auxActive / auxPassive の両方を返す） |
| base Lv7 前後 → 強化の重み | 接続済み（ただし**所持スキル全般**にかかる汎用補正で、進化元を狙っていない） |
| support 必要 Lv 直前 → 強化の重み | 部分的（`nearlyMaxedSkillWeightMultiplier` は maxLevel-1 のみ。必要 Lv が maxLevel と違う補助には効かない） |
| 条件成立後 → 進化提示 | 接続済み（最優先枠・未提示 0） |
| evolution partner 補正 | 接続済み |
| pity | **接続不良**（`draftsSinceProgress` は進化成立でしかリセットされず、補助側にしか効かない） |
| combined cap | 接続済み（`synergyAssistMaxMultiplier`） |
| minimum battle level | 接続済み |
| rarity weight | 接続済み |
| 満枠時の候補分類 | 接続済み（満枠で新規を出さず強化は出す） |
| **所持 support → base の重み** | **未接続（存在しない）** |
| active 補助の進化 | 接続済み（`ground_slam` も partner に入る） |

**結論**: 既存 synergy は「基礎を持っている → 補助を煽る」の**一方向しか無い**。
火 / 氷は補助が active 中心で基礎 Lv8 が相対的に早く埋まる設計なので露見しなかったが、
戦士は補助が passive 中心（早期に最大化される）で、**詰まるのは基礎 Lv8 の側**だった。
そこへ効く経路が production に無かったことが主因。

## 6. 採用した修正（詳細は `./warrior-evolution-guidance.md`）

`data/skill-config.json` の `guidance` ブロック（ジョブ限定）と、
`SkillDraftManager._guidanceMult()` を追加した。**skill ID のハードコードなし**（進化レシピから導出）。

- 所持している進化元の**強化**を優遇する（最大 Lv に近いほど強く）
- 補助が揃っている進化元は、さらに優遇する
- 必要 Lv 未達の補助を優遇する（必要 Lv 手前でさらに）
- 補助が**すでに揃っている**進化元の新規取得だけ、わずかに優遇する
- 導線が一定ドラフト進まなければ pity で段階的に強め、進んだらリセットする

## 7. 不採用にした案

| 案 | 不採用の理由 |
|----|--------------|
| 進化候補を強制挿入する / 条件未成立でも進化を提示する | 「guaranteed evolution の直接付与」に該当。仕様で禁止 |
| レベルアップ候補を進化 1 択へ固定する | 同上。build の自由が消える |
| 進化元の**新規取得**を無条件に優遇する | 実測でレアリティ階層を歪めた（rare の進化元 `war_cry` の取得率が同 rarity 中央値の 4.8 倍へ）。補助が揃っているときだけに限定した |
| slot4 のとき、進化軸と無関係な新 active の重みを抑制する | 実測で到達率がほとんど変わらず（88.7% → 88.7%）、build 多様性だけが下がったので**採用しなかった**。data のフィールドも残していない |
| 特定の進化 / スキルだけを優遇する | 仕様で禁止。集中が起きる |
| 候補生成後に候補を差し替える | 決定論と RNG 消費を壊す |
| テスト閾値を下げて結果へ合わせる | 仕様で禁止 |
| global な rarity / synergy を変える | 火 / 氷の非回帰を壊す |

## 9. 健全性（過剰誘導していないこと）

| 指標 | 前 | 後 |
|------|----|----|
| 最頻進化のシェア（枠4/40）| 34.8% | **30.4%** |
| 最頻進化のシェア（枠6/60）| 27.5% | **25.6%** |
| 最頻進化のシェア（枠8/80）| 20.4% | **20.1%** |
| build（所持 active の組み合わせ）の種類（枠4）| 61.9% | **66.5%** |
| build の種類（枠6 / 枠8）| 80.7% / 76.3% | **83.6% / 80.8%** |
| 取得率が同 rarity 中央値の 3 倍超（新規取得ベース）| 0 件 | **0 件** |
| 進化を持たない active の取得 | — | 枠4 で **+3.9%**（減っていない） |
| 候補ゼロ / 混入 / 重複 / 枠違反 | 0 | **0** |
| 条件成立後の未提示 | 0 | **0** |
| pity 発動率（枠4 / 40 lv）| — | 13.9%（毎ドラフトではない） |

**guidance はどの指標でも集中を悪化させていない**（むしろ多様性が上がっている）。
これは「どの進化元を取るか」をレアリティ階層に委ね、
「取った進化元を最後まで伸ばす」側だけを助ける設計にしたため。

### 残っている観測（警告ではない）

- **総ピック数**（強化を含む）で見ると `great_cleave` が同 rarity 中央値の 3.35 倍、`war_cry` が 3.65 倍。
  ただしこれは「深く伸ばした base はピック数が 8 回になる」ことによる指標の性質で、
  **新規取得率で見れば 0 件**。テストは新規取得率で判定している。
- 枠8 / **60** レベルアップだけ最頻進化シェアが 35% 前後になる（枠8 の標準は 80 レベルアップで 20.1%）。
  `great_cleave` が common である以上の構造的な偏りで、guidance 導入前は 40.7% だった。
